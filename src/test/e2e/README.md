# Расширенная проверка

Это постоянные инструкции запуска проверок. Артефакты создаются в `out/e2e/`; DOTM эти скрипты не изменяют и не генерируют.

## Быстрые проверки в CI

Workflow `ci.yml` выполняет проверку типов, lint, `test:unit`, API/CLI-проверки `run.cjs` без офисной постобработки и сборки npm/расширения на push в `develop`/`master`, pull request и при ручном запуске. Перед публикацией вызывается тот же workflow для выпускаемого коммита; сборка архивов и публикация начинаются только после успешных проверок. Состав TGZ/VSIX дополнительно сверяется с `file-snapshot.json`.

Настоящие офисные экспорты, VS Code extension host, браузерный интерфейс и Docker в CI не запускаются. Тяжёлые проверки выполняются отдельно по затронутым сценариям; команды приведены ниже. Для существующих проверок настоящего VS Code используйте `npm run compile-tests`, `npm run build:ext` и `npm run test:vscode`.

## Проверка LibreOffice

Требуются LibreOffice Writer/Math и Python 3.10+ с UNO. В Windows используется комплектный Python LibreOffice, в Debian/Ubuntu — пакеты `libreoffice-writer libreoffice-math python3-uno`. Для нестандартной установки задайте `SOFFICE_PATH` и `UNO_PYTHON_PATH`. Word для этих проверок не нужен.

```powershell
npm run build:npm
node src/test/e2e/libreoffice.cjs
node src/test/e2e/libreoffice_runtime.cjs
```

В Linux перед запуском укажите системный Python с UNO:

```bash
export UNO_PYTHON_PATH=/usr/bin/python3
node src/test/e2e/libreoffice.cjs
node src/test/e2e/libreoffice_runtime.cjs
python3 src/test/e2e/libreoffice_pdf_audit.py out/e2e/libreoffice
```

`libreoffice.cjs` проверяет четыре примера продолжений, оформление и вставки DOCX/PDF через публичный API. Сохранённые DOCX повторно открываются в Writer: проверяются границы фрагментов, номера, шапки, оглавление и повторная обработка. В PDF проверяются внутренние ссылки. Для одного сценария есть `--case=01-table-first`, `02-listing-first`, `03-boundaries`, `04-appendices`, `features` или `includes`.

`libreoffice_runtime.cjs` проверяет выбор движка, экспорт DOCX/PDF, ошибки, пути с Unicode, отмену, завершение дочерних процессов, параллельные задания и непомещающуюся строку. `libreoffice_pdf_audit.py` требует Poppler (`pdftotext`): проверяет сохранность и порядок маркеров, продолжения, границы страниц и вставки. PDF также нужно отрендерить `pdftoppm` и просмотреть визуально. Различия числа страниц между версиями LibreOffice и Word допустимы.

Для другого каталога артефактов задайте `MD2GOST_E2E_DIR`; тот же каталог передайте PDF-аудиту. Проверки запускаются локально, в том числе в подготовленном Docker-окружении. macOS не проверен.

После сборки TGZ/VSIX запуск `package-smoke.cjs` с `MD2GOST_TEST_LIBREOFFICE=1` дополнительно проверяет PDF через упакованные CJS/ESM/CLI. Каталог с архивами можно задать через `MD2GOST_PACKAGE_DIR`.

## Проверка API и Word

Из корня проекта:

```powershell
npm run build:npm
node src/test/e2e/run.cjs
node src/test/e2e/fixtures.cjs
```

`run.cjs` проверяет публичные CJS/ESM/CLI API, пути, ошибки, отмену, подстановки, настройки и геометрию DOCX. `fixtures.cjs` создаёт шесть `.g.md` и исходные DOCX: границы таблиц, сложные таблицы, листинги, смешанные разделы, оформление и заведомо непомещающаяся строка. Для повторения только затронутого сценария есть `--case=<имя>`.

Настоящая проверка исходников VBA в Word с уже разрешённым доступом к VBProject:

```powershell
& src/test/e2e/word-layout.ps1 -InputDoc out/e2e/layout/mixed-sections/raw.docx -OutputDoc out/e2e/layout/mixed-sections/processed.docx -RenderPDF
```

Runner открывает настоящий DOCX, сохраняет отдельную временную копию, загружает исходники VBA, выполняет макрос дважды и сравнивает структуру. `LayoutVerifier.bas` проверяет все маркеры, номера, шапки, границы фрагментов, подписи, ширины и изображения. Для negative fixture `oversized-row` передаётся `-ExpectedError 'do not fit'`. Полный обход абзацев есть только в проверяющем модуле; рабочий `AutoContinuation` использует Find/Tables.

```powershell
node src/test/e2e/pdf-pipeline.cjs
python src/test/e2e/audit_pdf.py out/e2e/pdf-pipeline/pdf-interleaved-includes/result.pdf --pipeline
python src/test/e2e/audit_pdf.py out/e2e/layout/mixed-sections/.md2gost_out/000-main.pdf --source out/e2e/layout/mixed-sections/raw.docx
```

PDF pipeline запускает публичный API с **тестовым runner, загружающим исходники**, и не подменяет проверку штатного DOTM. Проверяются вставки до оглавления и между разделами. Аудит проверяет адреса ссылок, порядок и полноту маркеров, подстановки и выход текста за страницы; для mixed-sections дополнительно проверяет отключение колонтитула. PDF нужно также отрендерить `pdftoppm` и визуально просмотреть. `contact_sheets.py <каталог> '<маска PNG>'` создаёт обзор страниц.

`package-smoke.cjs` сверяет реальные TGZ/VSIX с `file-snapshot.json` и экспортирует DOCX через CJS/ESM/CLI из распакованного TGZ. Зависимости разрешаются из рабочего проекта; это не проверка чистой установки из сети.

После правки повторяются только затронутые сценарии. Проверка исходников VBA во временном документе не заменяет проверку обычного `assets/run.ps1` с поставляемым шаблоном.

`standard-runner.cjs` проверяет обычный API DOCX со смешанными разделами и обычный CLI PDF со вставками между разделами. Перед запуском подготовьте layout fixtures и PDF fixtures командами выше: он использует их входные файлы и внешние документы. Скрипт запускает `assets/run.ps1` без загрузки исходников и сохраняет результаты в `out/e2e/standard-runner/results.json`. Контрольная сумма шаблона записывается для воспроизводимости; совместимость проверяется фактическим экспортом. После успешного запуска нужен итоговый PDF-аудит и визуальный просмотр; статус `passed-structural` означает только структурную проверку. `verify-standard.ps1` проверяет уже созданный DOCX read-only относительно raw-базы и экспортирует контрольный PDF, не запуская форматирование повторно.

После изменения только шаблона `package-smoke.cjs --assets-only` сверяет состав архивов и побайтовое равенство обоих упакованных DOTM актуальному шаблону, не повторяя независимые CJS/ESM/CLI-экспорты.

## Крайние случаи для VBA и Python UNO

После `npm run build:npm` запустите один или оба движка в соответствующем окружении:

```powershell
node src/test/e2e/macro-edges.cjs --engine=word
node src/test/e2e/macro-edges.cjs --engine=libreoffice
```

Оба движка получают одинаковые примеры: пустые и короткие блоки, многостраничный листинг с пустыми и длинными строками рядом с короткими листингами, таблицы с разными шапками, блоки без подписи и непомещающаяся строка. Проверяются номера продолжений, порядок данных, сохранность пустых строк кода, повторная обработка и доступность восстановленного DOCX при ошибке экспорта PDF. Для одного примера добавьте `--case=<имя>`. Результаты сохраняются в `out/e2e/macro-edges/`.

## Проверка продолжений таблиц и листингов

Примеры в `fixtures/continuations` используются тестами `src/test/e2e/continuations.test.ts`. Рабочий макрос продолжений — `AutoContinuation` из `resources/vba/AutoContinuation.bas`; `assets/run.ps1` вызывает его один раз. Для обычного экспорта используется поставляемый `assets/template.dotm`, для проверки исходников — отдельные временные документы.

Внешний проход находит следующую подпись листинга через `Range.Find` по стилю и следующую таблицу через `Range.Tables`, после чего выбирает ближайший элемент. Обычные абзацы документа не перебираются. Внутри найденного элемента проверяются строки кода или строки таблицы, чтобы определить границы страниц.

Преобразуйте каждый `.g.md` в DOCX обычной командой md2gost. Для пошаговой проверки можно сначала создать DOCX без постобработки и запустить `AutoContinuation` из Word вручную. Все команды ниже выполняются из корня проекта.

| Файл | Сценарий |
| --- | --- |
| `01-table-first.g.md` | Длинная таблица → длинный листинг → таблица → листинг; разбиение таблицы меняет размещение следующего листинга. |
| `02-listing-first.g.md` | Листинг → таблица → листинг → короткая таблица; проверка обратного порядка и коротких элементов. |
| `03-boundaries.g.md` | Короткие элементы после заполняющих абзацев, явный разрыв страницы, многостраничная таблица с многострочными ячейками и листинг с длинными строками. |
| `04-appendices.g.md` | Оглавление, приложения А и Б, номера А.1/Б.1, смена ориентации и повторный отсчёт страниц раздела. |

Ожидаемый результат:

- На каждой следующей странице элемента есть правильная подпись «Продолжение таблицы …» или «Продолжение листинга …», связанная со следующим содержимым.
- Подписи таблиц находятся вне ячеек; шапка каждого фрагмента повторяется.
- Маркеры `T…_ROW_001` и `L…_LINE_001` идут по порядку; ни один не пропадает и не дублируется. Они специально добавлены в каждую строку.
- Короткие элементы, целиком помещающиеся на странице, не получают лишних подписей.
- Повторный запуск макроса на том же документе не добавляет подписи, разрывы и копии шапок. Обновление номеров страниц в оглавлении при этом допустимо.

Число страниц зависит от версии Word, шрифтов и параметров принтера; фиксированного ожидаемого количества страниц нет.

`npm run test:unit` проверяет преобразование всех четырёх примеров в DOCX и сохранность маркеров, а также извлечение номеров из обычных подписей и продолжений через движок VBScript.

Дополнительная проверка настоящего VBA в Word:

```powershell
$env:MD2GOST_TEST_WORD = '1'
npm run compile-tests
node node_modules/mocha/bin/mocha.js --ui tdd out/test/e2e/continuations.test.js
Remove-Item Env:MD2GOST_TEST_WORD
```

Этот тест требует установленного Word и уже разрешённого программного доступа к проекту VBA. Исходный DOCX открывается из VBA через `Documents.Open`, чтобы обойти зависание прямого COM-вызова в Word 2007 и сохранить размеры страниц, поля и разделы. Исходники загружаются только во временные документы. В первых двух примерах проверяется отсутствие стилей продолжений и откат к стилям обычных подписей; в остальных — наличие `Listing_Cont` и `Table_Cont`. Макрос выполняется дважды; проверка разметки, подписей и шапок выполняется внутри Word модулем `src/test/e2e/helpers/InspectContinuations.bas`, а порядок и сохранность маркеров сверяются в PowerShell. DOTM и настройки безопасности не изменяются. Без переменной окружения проверки Word пропускаются. На медленном Word для каждого примера предусмотрен лимит 10 минут.
